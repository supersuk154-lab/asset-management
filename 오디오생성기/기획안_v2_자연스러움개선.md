## 1. 벤치마킹 조사 요약

| 프로젝트 | 라이선스 | 핵심 기법 | 우리가 가져올 것 | 채택 시기 |
|---|---|---|---|---|
| **Podcastfy** (NotebookLM 오픈소스판) | Apache 2.0 | LLM이 원문을 **구어체 대화로 재작성** 후 TTS (edge-tts 지원) | 구어체 리라이팅 단계, 대화 스타일 설정 분리 | ✅ **즉시 (Phase 2)** |
| **Dia** (Nari Labs) | Apache 2.0 | 대화 전체를 **한 호흡에 통으로 생성**, `(laughs)` 등 비언어음 합성 | 비언어 태그 어휘 표준, 향후 엔진 후보 | Phase 3 (GPU 필요, 영어 중심) |
| **ChatTTS** | AGPL/비상업 | 웃음·쉼·추임새를 토큰 단위로 세밀 제어 | 추임새를 대본 차원에서 명시하는 발상 | 발상만 차용 |
| **VibeVoice** (마이크로소프트) | MIT | 최대 4화자·90분 장편 대화 생성 | 다화자 확장 시 참고 | Phase 3 |
| **MOSS-TTSD** | Apache 2.0 | 다화자 대화 전용, 짧은 샘플 목소리 복제 | 향후 엔진 후보 | Phase 3 |
| **GPT-SoVITS** | MIT | **5초 샘플로 목소리 복제**, 한국어 기본 지원 (억양 다소 어색) | "내 목소리로 생성" 기능 | Phase 3 (선택) |
| **podcast_tts** | MIT | 배경음악(BGM) 트랙 + 볼륨 덕킹 믹싱 | BGM 오버레이 설계 | Phase 3 (선택) |

**조사 핵심 결론 2가지:**

1. **자연스러움의 8할은 TTS 음질이 아니라 '대본의 구어체 품질'에서 나온다.**
   Podcastfy가 증명한 방식 — 문어체 대본을 추임새("어...", "아 맞다")·맞장구("그치", "진짜?")·말줄임표가 살아있는 구어체로 LLM이 재작성하면, 같은 TTS 엔진으로도 체감 품질이 완전히 달라진다. 이 역할은 클로드 코드가 무료로 수행 가능 → **우리의 최우선 과제.**
2. **최신 대화 전용 모델(Dia 등)의 통합 생성 방식이 미래 방향이나, 전부 영어·중국어 중심 + GPU 필요.**
   한국어는 현재 edge-tts가 로컬 오픈소스 모델보다 안정적. 따라서 엔진 교체는 서두르지 않되, **비언어 태그를 지금부터 데이터에 보존**해 향후 갈아탈 때 무손실로 이전한다.

## 2. Phase 2 실행 계획 (이번 목표)

### 2-A. 구어체 리라이팅 단계 신설 — Step 1.5 ★★★ 최우선

```
[기존]  대본 → 파싱 → 합성 → 병합
[개선]  대본 → ★구어체 리라이팅(클로드)★ → 파싱 → 합성 → 병합
```

- **담당:** 클로드 코드 (파이썬 아님 — LLM 추론 영역)
- **동작:** 사용자가 준 원본 대본을 아래 규칙으로 재작성한 `{이름}_구어체.txt` 생성
  - 추임새 삽입: "어...", "음...", "아 그" (문장 시작부, 과하지 않게 대사 3~4개당 1회)
  - 맞장구 삽입: 상대 말에 대한 짧은 반응 ("그치", "아 진짜?", "맞아 맞아")
  - 문어체 → 구어체 변환: "그러하다" → "그렇지 뭐", 긴 문장은 짧게 끊기
  - 말줄임표(...)·대시(-) 배치: 망설임·말끝 흐림 연출 (edge-tts가 억양으로 반영)
  - **원칙: 정보(사실 내용)는 1도 바꾸지 않는다. 말투만 바꾼다.**
- **선택권:** 원본 그대로 / 구어체 버전 — 두 가지 모두 생성해 사용자가 비교 선택 가능

### 2-B. 감정 태그 → 음성 파라미터 자동 매핑 ★★

- 클로드가 대사별 감정·문맥을 분석해 dialogue.json에 값 기록, 파이썬이 그대로 적용
- 매핑 테이블 (`emotion_map.json`으로 분리 — Podcastfy의 설정 분리 방식 차용):

| 감정 태그 | rate | pitch | 뒤 무음(pause) |
|---|---|---|---|
| 신나서/반갑게 | +15% | +3Hz | 500ms |
| 슬프게/실망 | -15% | -3Hz | 1000ms |
| 놀라며 | +10% | +5Hz | 400ms |
| 멋쩍게/망설임 | -10% | ±0 | 900ms |
| (기본) | ±0 | ±0 | 700ms |

- 문맥 기반 무음 가변화: 질문 뒤 답변은 짧게(400ms), 화제 전환은 길게(1200ms)

### 2-C. 비언어 태그 어휘 표준화 ★

- 파서가 `(웃음)`, `(한숨)`, `(헛기침)` 등을 인식해 dialogue.json의 `nonverbal` 필드에 보존
- 현재 edge-tts에서는: `(웃음)` → "하하" 텍스트 치환 + rate 상승으로 근사 처리
- 향후 Dia/MOSS-TTSD급 엔진 도입 시: 보존된 태그를 `(laughs)` 형식으로 변환해 그대로 전달
- 표준 어휘 (1차): `웃음, 한숨, 헛기침, 침묵, 놀람, 속삭임`

### 2-D. 대화 스타일 프리셋 (Podcastfy conversation_config 차용) ★

- `styles.json`: 리라이팅 톤을 프리셋으로 관리
  - `친구수다` — 반말, 추임새 많음, 템포 빠름
  - `팟캐스트` — 진행자/게스트 역할, 존댓말, 정보 전달 중심
  - `드라마` — 감정 진폭 크게, 무음 길게
- 실행 시 지정: "이 대본 팟캐스트 스타일로 만들어줘"

## 4. 작업 순서 및 완료 기준

```
1. emotion_map.json + styles.json 생성          (설정 분리)
2. parse_script.py 확장: 비언어 태그 인식·보존     (2-C)
3. synthesize.py 확장: emotion_map 기반 파라미터 적용 (2-B)
4. merge_audio.py 확장: 대사별 가변 pause 적용     (2-B)
5. CLAUDE.md 작성: 구어체 리라이팅 규칙 성문화      (2-A, 2-D)
6. 검증: 동일 대본으로 [원본 vs 구어체] A/B 생성 → 청취 비교
```

**Phase 2 완료 기준:**
- 같은 대본의 원본 버전과 구어체 버전 MP3가 모두 생성되고, 구어체 버전에서 추임새·맞장구·감정별 템포 변화가 청취로 확인된다.
- 숫자·사실 정보는 원본과 100% 일치한다 (자산관리 프로젝트의 reviewer 원칙 준용).

## 5. 변하지 않는 것

- **비용 0원 유지** — 모든 추가 기능이 클로드 코드 세션 + 무료 도구 범위 내
- **PC 불필요** — GitHub Actions 자동화 흐름 유지 (대본 푸시 → MP3 자동 커밋)
- **엔진 격리 원칙** — TTS 교체가 synthesize.py 한 파일 수정으로 끝나는 구조 유지
- **WAV 중간처리 → 최종 1회 MP3 인코딩** 원칙 유지
